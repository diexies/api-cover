## Что такое APICover?

APICover — это работающий внутри процесса (in-process) **движок исследования пространства состояний (state-space exploration)** для HTTP API на ASP.NET Core. Наблюдаемое множество поведений REST API — функция не сигнатур эндпоинтов, а тройки *комбинации входных данных × порядок выполнения × разделяемое состояние*. OpenAPI/Swagger документирует лишь проекцию этого пространства — статическую поверхность контракта; топология ветвления бизнес-процессов (политики повторных попыток оплаты, нарушения идемпотентности, каскады soft-delete, подверженная гонкам генерация slug'ов) не представима ни в одном формате спецификаций. Именно этот разрыв в представлении — причина существования APICover.

Архитектурно он работает в три слоя:

**1. Живое обнаружение (live discovery).** APICover — не прокси, не sidecar и не внешний агент; он регистрируется в DI-контейнере через `AddAPICover()` и в middleware-конвейере через `UseAPICover()`. Инвентарь эндпоинтов он читает из собственной абстракции ASP.NET Core — `IApiDescriptionGroupCollectionProvider`, то есть питается ровно из того же источника истины, который разрешает слой маршрутизации фреймворка. Никакого вручную поддерживаемого spec-файла, никакого риска расхождения (drift), никакого шага кодогенерации. Поверх этого добавляется **статический анализ графа вызовов на уровне IL**: движок обходит скомпилированное тело каждого эндпоинта, разрешает диспетчеризацию DI-интерфейсов до конкретных реализаций, классифицирует внешние HTTP-вызовы и границы баз данных (I/O boundaries). Чёрный ящик становится прозрачным снаружи внутрь.

**2. Декларативная композиция сценариев.** Сценарии — это **DAG** (направленные ациклические графы), собираемые на холсте: узлы — HTTP-вызовы, рёбра — зависимости по данным и порядку. Движок планирует граф **конкурентно, через топологическую сортировку** — независимые ветки выполняются параллельно. Поток данных между узлами описывается выражениями **JSONLogic** вместо императивного связующего кода: шаблоны path, query, заголовков и тела разрешаются против живого `RunContext`, несущего ответы вышестоящих узлов (`nodes.<id>.response.*`). Без фикстур, без сериализационного шаблонного кода — привязка данных полностью декларативна.

**3. Комбинаторное ветвление (branched execution).** Отличительный механизм — **Case Set**: набор вариантов, прикрепляемый к любому узлу, с N вариантами и переопределениями на уровне полей. Когда выполнение достигает этого узла, движок применяет **семантику fork** — глубоко клонирует (deep clone) `RunContext` для каждого варианта и изолированно повторно выполняет нижестоящее поддерево для каждой ветки. При вложенных Case Set'ах ветки множатся **декартовым произведением**: 3 варианта на login × 2 на checkout = 6 полностью трассируемых веток с независимыми проверками за один запуск. Комбинаторный взрыв под контролем: **предполётный оценщик веток (pre-flight branch estimator)** вычисляет число веток до запуска и отклоняет превышающие лимит; во время выполнения вторую линию обороны образуют ограничение конкурентности на семафоре и атомарные счётчики (`MaxBranches=128`, `MaxConcurrentBranches=16`, `MaxLeafInvocations=4000`).

Каждая ветка порождает собственную трассу и вердикт pass/fail с ключом `(nodeId, BranchPath)`; жизненный цикл веток публикуется в реальном времени по SSE. Итоговый артефакт — **древовидная матрица покрытия** поведений, которые ваш API может проявить в заданном пространстве входных данных: первоклассный, порождаемый движком эквивалент того, что раньше имитировали, клонируя одну и ту же коллекцию Postman двенадцать раз и синхронизируя её вручную.

## Какова цель?

Целевой пользователь APICover — разработчик, который выпустил работающий API на ASP.NET Core, но не писал весь код под ним или не владеет им полностью, — всё более частая ситуация в кодовых базах, созданных с помощью ИИ. Вы смотрите в Swagger и видите список эндпоинтов; но поведения системы (процесс покупки, провижининг пользователей, повторные попытки оплаты) не видны нигде.

Каждый существующий инструмент покрывает лишь один срез тестирования API:

| | Живое обнаружение | Визуальный поток | Ветвящееся пространство состояний | Регрессия по веткам |
| --- | :---: | :---: | :---: | :---: |
| Postman / Insomnia | — | — | — | — |
| Cypress / Playwright | — | — | — | — |
| k6 / JMeter (нагрузка) | — | — | — | — |
| WireMock / MockServer | — | — | — | — |
| Hypothesis / property-based | — | — | частично | частично |
| **APICover** | **✓** | **✓** | **✓** | **✓** |

Никто не объединяет все четыре: **живое обнаружение системы + визуальное редактирование потоков + исследование ветвящегося пространства состояний + обнаружение регрессий по веткам.** Именно этот пробел закрывает APICover.

Коротко: **альтернатива Postman** для команд, которым важны поведения; **альтернатива Swagger** для команд, которые хотят видеть саму систему, а не только её поверхность.

## Где применять?

- **Извлечение покрытия поведений** — увидеть за один запуск все пути, которыми ваш API может пройти бизнес-процесс (заказ, счёт, оплата), и отслеживать pass/fail по каждой ветке.
- **Понимание и проверка кода, сгенерированного ИИ** — увидеть снаружи внутрь, что на самом деле делает бэкенд, который вы писали не целиком: через инспекцию графа вызовов на уровне IL (включая конкретные реализации за DI-интерфейсами, внешние HTTP- и БД-границы).
- **Ловля регрессий** — сохранять сценарии и перезапускать после каждого изменения; видеть, какая именно *ветка* сломалась — на уровне поведения, а не эндпоинта.
- **Избавление от дублирования коллекций Postman** — вместо клонирования коллекций ради «тот же поток, другие входные данные» прикрепить Case Set к одному сценарию.
- **Многошаговые интеграционные тесты** — без связующего кода и фикстур; поля path, query, заголовков и тела питаются инлайновыми JSONLogic-выражениями от ответов вышестоящих узлов.
- **Тестирование потоковых эндпоинтов** — SSE, NDJSON и сырые chunk-потоки, с условными правилами `until`, завершающими поток досрочно.
- **Исследование и отладка** — поставить breakpoint и остановиться на узле, отредактировать запрос и продолжить; повторить подграф N×M раз с мутациями на каждой итерации (Execution Groups).
- **Поручить написание тестов ИИ** — дать LLM в вашей IDE (Cursor, Copilot, Claude Code, Cline…) читать инвентарь эндпоинтов по MCP, набрасывать сценарии, запускать их и докладывать о сломанных ветках. Подробности ниже.

## Как это работает?

Установка — два пакета и три строки:

```bash
dotnet add package APICover
dotnet add package APICover.UI.Web
```

```csharp
using APICover.Hosting;
using APICover.UI.Web;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddAPICover();
builder.Services.AddAPICoverWebUI();

var app = builder.Build();
app.UseAPICover();   // откройте /apicover/ui/ в браузере
app.MapControllers();
app.Run();
```

Запустите приложение, откройте `/apicover/ui/` — ваши эндпоинты уже на холсте.

Ключевые архитектурные решения:

- **Без прокси, без SDK, без агента.** APICover — внутрипроцессное middleware; маршруты он читает из собственного `IApiDescriptionGroupCollectionProvider` ASP.NET Core — видит ровно то, что маршрутизирует фреймворк, и отдельно поддерживаемого spec-файла не существует.
- **Защита от взрыва пространства состояний.** Предполётный оценщик веток плюс ограничения времени выполнения (`MaxBranches`, `MaxConcurrentBranches`, `MaxLeafInvocations`) заранее отклоняют неконтролируемо растущие запуски.
- **Подключаемое хранилище.** По умолчанию in-memory; провайдеры SQLite, SQL Server и PostgreSQL подключаются без изменения кода приложения. Сценарии и запуски хранятся как документы в стиле JSONB — никаких EF-миграций для сопровождения.

## Жизненный цикл теста

Путь поведенческого теста внутри APICover проходит пять стадий:

1. **Обнаружение (discovery).** При старте приложения APICover инвентаризирует каждый контроллер и minimal-API-эндпоинт из таблицы маршрутов; при включённом `EnableCallGraphInspection` извлекает IL-граф вызовов для каждого эндпоинта. Ни один написанный вами тест не может ссылаться на несуществующий путь — инвентарь является единственным источником истины.
2. **Композиция (authoring).** Вы строите DAG, соединяя узлы на холсте, либо пишете JSON сценария напрямую (вручную или через LLM). Зависимости по данным между узлами объявляются через JSONLogic; `scenarios.save` при сохранении валидирует формат id и целостность рёбер (edge integrity) — несвязный граф сохранить нельзя.
3. **Выполнение (execution).** Движок планирует граф в топологическом порядке, гонит независимые ветки параллельно и делает fork на узлах с Case Set. Запуск живой: события узлов и веток (`BranchSpawned`, `BranchCompleted`) текут по SSE; можно остановиться на breakpoint'е, отредактировать запрос и продолжить, пропустить ветку или прервать запуск.
4. **Вердикт (assertion).** Каждый узел каждой ветки порождает собственный результат с ключом `(nodeId, BranchPath)`; pass/fail агрегируется по листьям, и в древовидном представлении напрямую читается, какая комбинация вариантов сломалась. Упавшие узлы сохраняются в записи запуска с деталями ошибки (`statusCode`, `error`).
5. **Регрессия (история + перезапуск).** С включённым постоянным хранилищем сценарии и история запусков переживают перезапуски. Вы перезапускаете тот же сценарий после каждого изменения и получаете diff на уровне веток: сигнал не «эндпоинт всё ещё возвращает 200», а «сломался вариант частичной оплаты в процессе возврата».

## ИИ-агенты и интеграция с MCP

APICover общается с LLM по двум отдельным каналам — писать тесты вручную не обязательно:

**Встроенный агент Claude** (пакет `APICover.Agent`). Добавляет в дашборд вкладку Agent: чат, рабочий процесс сканирования системы (scan) и память проекта. Два режима учётных данных — ключ Anthropic API, вставленный в UI, либо сессия подписки через локально установленный CLI `claude`. Агент набрасывает сценарии *изнутри* приложения, имея доступ к обнаруженному инвентарю эндпоинтов и графу вызовов.

**MCP-сервер** (пакет `APICover.Mcp`). Открывает **19 инструментов** по протоколу Model Context Protocol, чтобы LLM в вашей IDE (Cursor, VS Code Copilot, Cline, Windsurf, Zed, Claude Desktop, Claude Code) могла программно управлять всей поверхностью APICover. Поддерживаются два транспорта: **streamable HTTP** на том же хосте (`/apicover/mcp`) и **stdio**, устанавливаемый как глобальный dotnet tool (`APICover.Mcp.Stdio`).

Каталог инструментов делится на шесть групп:

| Группа | Инструменты | Назначение |
|---|---|---|
| Сценарии | `scenarios.list` · `get` · `save` · `delete` · `run` | CRUD сценариев + запуск; `save` валидирует схему и целостность рёбер |
| Запуски | `runs.list` · `list_failed` · `get` · `subscribe` | Запросы к истории; `list_failed` возвращает строку на каждый упавший узел, `subscribe` стримит прогресс вживую |
| Эндпоинты | `endpoints.list` · `details` | Проекция инвентаря — область, назначение, параметры, примеры тел, auth |
| Память | `memory.list` · `read` · `write` · `append` · `delete` | Знания о проекте, изолированные по путям (path-sandboxed) под корнем памяти агента |
| Покрытие | `coverage.summary` · `uncovered_endpoints` | Что протестировано, где пробелы |
| Git | `git.commit_impact` | Diff → затронутые сценарии по файлам: «что сломает этот коммит?» |

Типичная MCP-сессия выглядит так: плейбук сессии, отдаваемый по адресу `{prefix}/api/mcp/playbook`, один раз вставляется LLM; после этого фраза *«напиши сценарий для `POST /invoices`»* заставляет модель прочитать реальную схему через `endpoints.details`, набросать JSON сценария, получить ваше одобрение, прогнать его через `scenarios.save` + `scenarios.run` и вживую докладывать результаты веток по `runs.subscribe`. Вопрос *«коммит `abc123` что-нибудь сломал?»* превращается в цепочку `git.commit_impact` → запуск затронутых сценариев → сводка сломанных веток; вопрос *«что тестировать дальше?»* — в `coverage.uncovered_endpoints` → приоритизированное предложение.

Плейбук также навязывает дисциплину агента: выдумывать пути, которых нет в инвентаре, запрещено; перед `scenarios.save` обязательно показать payload и получить одобрение; удаления требуют явного подтверждения в том же ходе; секреты из примеров тел нельзя выводить обратно в чат.

## Технологии

- **Backend**: .NET 8, ASP.NET Core, C# 12, EF Core 8 (хранилище), JSONLogic, JSON Path
- **Frontend**: React 18, TypeScript 5.6, Vite 5.4, XyFlow 12 (холст), Dagre (раскладка)
- **Хранилище**: in-memory · SQLite · SQL Server · PostgreSQL
- **Лицензия**: MIT
